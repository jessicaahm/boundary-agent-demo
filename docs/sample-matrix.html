Boundary RBAC Matrix

Seven roles, three effective principals, one target. Boundary has no general policy object — policy covers only session-recording retention, and this cluster has none — so all authorization is expressed as grant strings on roles. Every cell below is read from grant_strings and grant_scope_ids as they stand now.

What the matrix exposes

Ordered by what would bite first, not by resource.

Blocking

Only admin can open a session

No role grants authorize-session on any target. A signed-in non-admin user can list and read kubernetes-api and would see it in the CLI — then fail at connect time. Delegating access to this cluster is currently impossible without handing over the admin account.

Single point

One account carries every privilege

Four users exist but only acctpw_uwO3OSEVaa can sign in, and it is the sole principal on all three Administration roles. Lose it and the only way back is the recovery KMS workflow — which audits as u_recovery, not as a person.

Scaling

Zero groups, so every grant is user-direct

All seven roles bind a user or a pseudo-user. There is no group and no managed group, so onboarding a second operator means editing role principals rather than adding a member — and there is no OIDC or LDAP auth method to drive managed groups from.

Noise

Four of the seven roles are dead weight

The global Administration role already reaches descendants, so the org and project Administration roles grant admin nothing new. The org Login and Default Grants role likewise repeats global Login Grants, adding only auth-token:list inside devops. They are harmless today but they make the real grant surface harder to read.

By design

Unauthenticated callers can enumerate scopes and auth methods

u_anon holds scope:list and auth-method:list,authenticate across global and all descendants. This is Boundary's default so that login works before a token exists, but it does mean scope names — devops, kubernetes — and the login endpoint are visible pre-auth.

Inert

No retention policy, because nothing is recorded

Zero storage policies, zero storage buckets, zero session recordings, and both HCP-managed workers report local_storage_state: not configured. If recording is ever switched on for kubernetes-api, there is no retain_for / delete_after policy attached to govern it.

Shortest path to a delegable setup

  1. Create a group in o_evm6LNcPVV — say k8s-operators — so membership stops being a role edit.
  2. Add a role in p_OMn1NpwlnP with grant_scope_ids=["this"] and the one grant that is missing: ids=ttcp_YPVQ1fCZ8v;type=target;actions=authorize-session,read.
  3. Bind the group as principal on that role. The existing Default Grants role already gives those users session:list,read:self,cancel:self, so no second session grant is needed.
  4. Add a second admin account under ampw_VwPciyixsN and put it on the global Administration role, so recovery KMS stops being the only break-glass.
  5. Delete the three redundant roles once a real second principal exists — not before, since they are the only scope-local admin hooks today.
